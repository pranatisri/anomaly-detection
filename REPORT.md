# AI-Powered Behavioural Anomaly Detection for Cybersecurity

**Report — assumptions, metrics, and known limitations.**

A defensive detection system that models "normal" access and connection behaviour per
entity, detects intrusion and compromised-credential activity in near real time,
classifies the anomaly type, and gives a SOC analyst an explainable risk score. All data
is synthetic and generated by us; the labels exist for training and evaluation only and
are physically separated from anything the detector can read.

---

## 1. The problem we actually had to solve

The stated task is detection. The *harder* problem, and the one most of this work went
into, is that **a synthetic benchmark can be solved without doing detection at all.**

If the generator and the detector encode the same assumptions, the detector rediscovers
the generator's parameters and posts near-perfect numbers that mean nothing. We therefore
wrote down, before producing any result:

> With confounders at 3–5× the attack rate and difficulty δ = 0.5, we expect incident
> PR-AUC ≈ 0.5–0.8. **A score near 0.99 is a bug report, not a result.**

That prediction is in `RESULTS.md`, recorded before the first number existed. The final
held-out figure is **PR-AUC 0.613**, inside the predicted band.

### The artefact audit caught four real leaks

We built an adversarial audit (`src/audit.py`) that hands a gradient-boosted classifier
*only* features carrying no legitimate behavioural information — row position in the file,
string lengths of opaque identifiers, float formatting precision, a random hash bucket of
the source IP, field-presence flags — and requires it to score **ROC-AUC ≤ 0.60**.

It failed on the first run at **0.9963**, and the diagnosis was worth the whole exercise:

| # | Defect | Effect |
|---|---|---|
| 1 | The audit's **own** train/test split was random | Any high-cardinality identifier scored ~1.0 by memorising campaign membership. Fixed with a campaign-grouped split. |
| 2 | Campaign start days compressed into the first third of the window | Row position predicted the label at 0.94 |
| 3 | `sso/read` was 58% attack traffic | Resource-string *length* predicted the label at 0.83 |
| 4 | Attacks drawn uniformly over entities, not over traffic | 74% of attacks hit users vs 54% of benign traffic; leaked through every entity-type proxy |

Defect #1 is the one worth dwelling on: it was a flaw in the *measuring instrument*, not
the generator, and taking it at face value would have meant rewriting a generator that
was less broken than it looked.

### It then failed twice more, on leaks our own fixes introduced

Tightening the service-account and edge-device cohorts (limitation 14) changed the traffic
profile and broke the gate again, 0.55 → **0.77**. Three further causes:

| # | Defect | Effect |
|---|---|---|
| 5 | Sparse campaigns left temporal gaps — 35 campaigns over 62 days, none in the first week | "attacks never happen before day 7" generalises: row position 0.77 |
| 6 | Attacks ignored the weekly cycle: placed uniformly by calendar day while benign traffic halves at weekends | weekend attack **rate** 4.07× weekday (Sun 3.80% vs Mon 0.11%) |
| 7 | `low_and_slow` minted devices with invented firmware from an 800-way space | `fw-2.9.15` appeared 58 times, **100% malicious** — one rule solves it |

Fixed by stratified campaign placement, weighting placement by benign traffic density
(weekend ratio 4.07× → ~0.9×), and cloning devices from the existing fleet — applied to
`insider_drift` and the benign `device_refresh` confounder too, since a clone-only-on-attack
asymmetry is just a tell pointing the other way.

Defect 7 was caught by the **exclusivity scan**, not the AUC gate, which passed at 0.4983
on that seed. Two independent checks, and the quieter one fired.

### The gate itself was under-powered

Seed 3 then failed at 0.6036 against a 0.60 line — a 0.004 margin. Measuring the
estimator's variance across 10 grouped splits *before* changing anything:

| seed | mean | sd | runs over 0.60 |
|---|---|---|---|
| 1 | 0.3725 | 0.0851 | 0/10 |
| 3 | 0.4222 | 0.0668 | 0/10 |

**sd ≈ 0.07.** A single split was deciding pass/fail by which `random_state` happened to be
hard-coded. The gate now averages 7 grouped splits and reports the spread.

**Final: seed 1 = 0.3591 ± 0.0847 PASS · seed 3 = 0.4342 ± 0.0448 PASS.** Vocabulary
exclusivity clean on both. All datasets were regenerated after every generator change, so
no number in this report mixes pre- and post-fix data.

## 2. Assumptions

**About behaviour.** Entities have stable habitual hours, a home city, a small set of home
IPs, a role-conditioned resource affinity, and one device. Humans are weekday- and
daytime-biased; service accounts run continuously with a nightly batch; edge devices are
flat and narrow. "Normal" is per-entity, not global — a 3 a.m. login is unremarkable for a
service account and notable for a salesperson.

**About attacks.** They are *campaigns*, not points: a start, an end, and many member
events. A brute force emits ~50 events; an impossible-travel emits three; a low-and-slow
spreads over weeks.

**About benign life.** It is messy. This is the assumption most synthetic benchmarks get
wrong, and we injected **benign confounders at 4× the attack rate**, each engineered to
trip a specific detector layer:

| Confounder | Trips |
|---|---|
| Business travel, airport VPN egress | geo-velocity |
| Password-reset storm, expired-cert retry loop | failed-auth rate |
| OS patch, firmware update, laptop refresh | fingerprint mismatch |
| On-call rotation, maintenance window | habitual-hour |
| Project onboarding, role change | novelty, new-edge |
| CI / automation burst | sequence surprisal, session duration |
| Shared jump host, office NAT | IP-level fan-out |
| Service-account credential rotation | auth-method change |

Without these, "unusual" and "malicious" become synonyms and precision is meaningless.

**Deliberately visible to the detector:** role / peer-group structure. An enterprise really
does have an HR system, and peer-relative reasoning is a legitimate technique. What makes
it safe is that roles drive *benign* resource assignment too — they are not attached only
to attacked entities.

**Hidden from the detector, always:** every per-entity behavioural parameter (habitual
hours, home geo, resource affinity, device fingerprint), the contamination rate, the
attack roster, campaign membership, every per-attack knob, the RNG seed, and δ itself.

## 3. Architecture

Layered, not monolithic. A single opaque scorer would fail the explainability requirement
and need slow, vague post-hoc attribution. Here **every contributing signal is already a
named, signed, unit-ed quantity**, so explanation is a sort rather than a reconstruction.

| Layer | Content |
|---|---|
| **L0** deterministic | Geo-velocity, failed-auth rate windows, device fingerprint mismatch |
| **L1** per-entity baseline | Habitual-hour histogram, known IP/geo/resource/device sets, session-duration distribution |
| **L2** sequence | Interpolated variable-order Markov surprisal over a flattened typed token stream |
| **L3** graph | Entity–resource bipartite graph: new edges, cohort corroboration |
| **L4** fusion | Correlation-corrected Stouffer → calibrated risk score; alerts scored by size-calibrated Stouffer over member events |
| **L5** type classifier | Rule-based attribution over the evidence vector; never raw fields |
| **L6** explanation | Ranked contributing signals with analyst-facing text |

**21 named signals** across three aggregation levels (13 entity / 3 IP / 5 long-window).

### Does the layered architecture earn its keep? — measured

Each layer was disabled in turn and the whole downstream pipeline refit (reference
distributions, weights, correlation correction, calibration, threshold), so each row is a
detector genuinely built without that layer. Run across **four eval seeds**, because a
single seed cannot distinguish a small effect from run-to-run variation — the same
objection that applies to the δ-sweep (limitation 9). `python src/ablation.py`.

**Δ Precision@1% vs the full model:**

| removed | mean | min | max | verdict |
|---|---|---|---|---|
| **L0** deterministic rules | **−0.389** | −0.539 | −0.208 | load-bearing |
| **L3** graph / long window | **−0.150** | −0.235 | −0.008 | load-bearing |
| L1 per-entity baseline | −0.004 | −0.033 | +0.025 | straddles zero |
| L2 sequence | +0.008 | −0.016 | +0.024 | straddles zero |

**Δ incident recall vs the full model:**

| removed | mean | verdict |
|---|---|---|
| L0 | −0.180 | negative on every seed |
| L3 | −0.078 | negative on 3 of 4 |
| L1 | −0.043 | negative on 3 of 4 |
| L2 | +0.031 | straddles zero |

Per-attack-type campaign recall on the seed-3 pair, which shows *where* the load-bearing
layers act:

| configuration | brute_force | device_spoofing | impossible_travel | lateral_movement | low_and_slow |
|---|---|---|---|---|---|
| full | 0.60 | 0.80 | 0.60 | 1.00 | 0.90 |
| without L0 | **0.20** | **0.30** | **0.30** | 1.00 | 0.90 |
| without L1 | 0.60 | 0.60 | **0.30** | 0.80 | 0.80 |
| without L2 | 0.60 | 0.80 | 0.60 | 1.00 | 0.90 |
| without L3 | **0.30** | 0.70 | 0.60 | 1.00 | 0.70 |

**What this shows, including where it contradicts the design claim:**

**L0 is load-bearing**, by a margin far outside plausible seed variation: −0.389 mean
Precision@1%, negative on every seed, never closer to zero than −0.208. It collapses brute
force (0.60 → 0.20), device spoofing (0.80 → 0.30) and impossible travel (0.60 → 0.30).
The cheap deterministic rules carry the sharp, single-event attacks.

**L3 is load-bearing**, −0.150 mean and negative on all four seeds, though one seed shows
only −0.008. Brute force halves without it (IP fan-out lives here) and `low_and_slow` drops
0.90 → 0.70 (the long-window signals).

**L1 contributes to coverage, not to precision.** Its Precision@1% effect straddles zero
(−0.004 mean, +0.025 on one seed), but incident recall is negative on 3 of 4 seeds
(−0.043 mean), and it clearly matters for impossible travel (0.60 → 0.30) and lateral
movement (1.00 → 0.80). It broadens what is found rather than sharpening the top of the queue.

**L2's contribution is not distinguishable from zero.** Removing the sequence layer
changes no headline metric and no per-type recall on any seed tested; across four seeds its
Precision@1% delta is **+0.008 with a range of [−0.016, +0.024]** and its incident-recall
delta **+0.031**, both straddling zero. Note the sign: on average, removing L2 very
slightly *improves* precision — so "L2 is neutral" is the generous reading, not a
conservative one. §3 previously asserted that every layer contributes; on this evidence
that claim does not hold for L2.

> **Scope this null result to this generator.** Command sequences here are produced by a
> small per-entity Markov chain, and L2 is n-gram surprisal over a flattened token stream.
> On Markov-generated sequences, n-gram surprisal is largely recoverable from per-event
> novelty — which L1 already supplies — so the two layers are substantially redundant *by
> construction of the benchmark*. The finding is that **L2 adds nothing on data with this
> much sequence structure**, not that sequence modelling is worthless. Real command
> streams have longer-range structure that an n-gram over a 2-token context cannot
> represent and that L1 would not capture.

*(Verification: without-L1 and without-L2 both round to Precision@1% 0.892 on seed 3. The
underlying values differ — 0.8924 vs 0.8917, TP 1178 vs 1177 of k=1320, with the selected
event sets overlapping only 92% — so both ablations took effect and the tie is 3-dp
rounding of a discrete count-based metric, not one ablation failing to apply.)*

### Three levels, never pooled

`credential_stuffing` is an **IP-level** phenomenon (many entities, few IPs);
`low_and_slow` only exists over **days**. A per-event, per-entity detector misses both by
construction, no matter how good the model is. Each level gets its own reference
distribution, calibration, threshold and alert budget.

### Fusion, and why labels barely touch it

Naive summing double-counts: geo-velocity, country-novelty and IP-novelty all fire
together on impossible travel, so a plain sum reports one event as three independent
alarms. We use correlation-corrected weighted Stouffer, `Z = (w·z)/√(wᵀΣw)`, with Σ
estimated on reference traffic — redundant signals inflate the denominator and stop
counting twice. Weights are analyst priors divided by an unsupervised reliability term;
they are **never learned from labels**, because learning them is learning the generator's
wiring diagram.

Labels enter at exactly one point: a **1-D monotone map** from the fused score to a
probability. A monotone scalar transform cannot re-weight features, so it cannot memorise
the generator — it can only stretch the axis so "top 1%" means something probabilistic.

### Alert scoring — a multiple-comparisons problem

An alert is an entity-window aggregate spanning tens to hundreds of events, so **alert
size is a confound**: a 200-event window gets 200 chances to contain a high score. The
original `top2mean(member scores)` correlated **0.263** with alert size, which meant the
queue ranked entities by how busy they were: only 7 of the top 30 alerts were malicious,
and 19 of 30 were service accounts — the cohort with the most events per entity — against
29.8% of traffic.

The fix is three coupled changes:

1. **Per-event p ranked within the live cohort.** Reference-based p left mean benign z at
   +0.13 rather than 0, and any accumulating statistic multiplies that by √n.
2. **Stouffer** `Σz/√n` — calibrated in n, still accumulates evidence.
3. **Empirical size calibration** against alerts of the same size, with spread taken from
   the **lower half only** (`median − q16`), because large alerts are disproportionately
   malicious and a two-sided MAD is inflated by the very attacks being ranked.

Result: correlation of alert score with alert size **0.263 → 0.042**, and the queue stops
being dominated by the busiest cohort — service accounts fall from 19 of the top 30 to a
share in line with their 30% of traffic.

Deliberately **not** claimed here: an improvement in top-20 malicious count. An earlier
draft cited 5 → 17, measured on a generator later found to be leaking. The current,
post-regeneration figure is 7/20, and the meaningful result is *what the false positives
are* rather than how many there are — see §5.

Two principled-looking alternatives were tried and rejected on measurement: a Šidák
correction on the best member event (kills brute force, 1.000 → 0.000, by discarding n−1
events) and Fisher's method (compounds per-cohort offsets; correlation rose to 0.619).

**`burst_ratio`** then restores what size calibration legitimately removes: activity
relative to *that entity's own* habitual rate rather than absolute volume. A service
account emitting 200 events an hour is doing its job; an account that normally emits two
doing the same is the attack. It measures 60.75 for brute force against 1.05 for normal.

### Mitigating signals — an exculpatory path

Every aggregator above is monotone *increasing*, so evidence of innocence could not lower
a score, and `insider_drift` sat at 47% HIGH against a ≤15% target. We added
`corroboration_7d` as an explicitly **subtracted** signal: five teammates gaining the same
access in the same week is evidence of onboarding, not intrusion. Only positive mitigation
counts — absence of corroboration must not raise a score.

The larger fix was making `resource_surprisal` an **excess over the role expectation**:
`max(0, entity_bits − role_bits)`. Raw per-entity surprisal scored "new to you but standard
for your team" identically to "new to you and unheard-of for your team", which is exactly
the insider-drift / lateral-movement confusion.

## 4. Metrics — and why the obvious ones are wrong here

Anomalies are 0.5–3% of events. We therefore **never** headline plain accuracy (meaningless
under this imbalance) or ROC-AUC (optimistic). No metric appears without the alert budget
or threshold it assumes.

### Events are collapsed into alerts before scoring

Without this, a 50-event brute force contributes 50 detections and a 3-event
impossible-travel contributes 3 — so recall silently becomes a measure of *event density*
rather than of detection, and a detector that nails brute force alone scores excellently.

### Two ceilings we report rather than hide

**`Recall@1% ≤ budget_fraction / prevalence`.** At 3% prevalence the ceiling is 1/3, and a
*perfect* detector still cannot exceed it. Every reported `Recall@1%` is printed with its
prevalence and its ceiling, and **R-Precision** (same formula with `k = |A|`) is always
reported beside it because it has no such artefact.

**`Incident_Precision@K ≤ n_campaigns / K`.** There are only so many campaigns to find.
Reporting precision without this cap is reporting the budget, not the model.

### Redundant alerts

Multiple reviewed alerts on one campaign yield exactly **one** true positive; the extras
are neither TP nor FP, but they **do** count toward alerts/analyst/day. Detection quality
is lenient; workload is strict.

The metric module and its 13 hand-computed tests (`tests/test_evaluate.py`) were written
**before any model existed**. If the metric definition moves after models are built, every
earlier result is void.

## 5. Results

Fitted on seed 1, evaluated on **seed 3 (held out)** and then on **five further held-out
seeds** under a hash-frozen config, at δ = 0.5.

Scale is requested as `--entities 200 --days 60`, but CM8 randomises both per seed so that
nothing about the benchmark can be hardcoded. Actual sizes: **seed 1 = 200 entities × 65
days (172,417 events)**, **seed 3 = 175 entities × 56 days (131,981 events)**. Any figure
quoted as "200 × 60" elsewhere is the CLI request, not what ran.

Seed 3 is the demo/eval seed because it carries all six attack types; seed 2 structurally
lacks `impossible_travel` (CM8 omits one type per seed).

### Headline — dev vs five held-out seeds

| Metric | dev (seed 3) | holdout (mean of 5) | gap |
|---|---|---|---|
| **Incident_Recall@K** | 0.817 | **0.837** | **+0.020** |
| **R-Precision** | 0.615 | 0.570 | −0.045 |
| **PR-AUC** | 0.643 | 0.613 | −0.030 |
| Precision@1% | 0.867 | 0.641 | −0.226 *(prevalence ceiling, §4)* |
| alerts/analyst/day | 9.0 | 10.2 | — |

Holdout prevalence varies ~3× across seeds (1.9% down to 0.6%) because the generator
randomises contamination per seed. That is generator sampling, not detector instability —
and it is exactly why Precision@1% swings while the prevalence-robust metrics do not.

### Per-attack-type campaign recall (five held-out seeds)

| Type | Recall |
|---|---|
| credential_stuffing | **1.000** |
| lateral_movement | **0.982** |
| low_and_slow | **0.971** |
| brute_force | 0.833 |
| device_spoofing | 0.657 |
| impossible_travel | 0.588 |

`brute_force` reads **0.600 on the dev seed against 0.833 on the holdout**, the same
dev/holdout spread limitation 3 records for `low_and_slow`: with roughly ten campaigns of
a given type per seed, a single seed's per-type recall carries ±0.2 of sampling noise. The
holdout mean over five seeds is the figure to use. (An earlier draft quoted 0.400 for the
dev seed; that predates the final regeneration.)

### Difficulty sweep — the headline degradation

`Precision@1%` and `PR-AUC` are the reported degradation signals because both are
**monotone**. Incident recall is not, and the reason is a confound rather than a defect:
prevalence falls 2.4% → 1.5% across the sweep, so at low δ more campaigns compete for the
same fixed budget K and recall becomes budget-saturated rather than detector-limited.

| δ | Precision@1% | PR-AUC | R-Precision | *incident recall* |
|---|---|---|---|---|
| 0.00 (blatant) | **0.965** | **0.699** | 0.600 | *0.600* |
| 0.25 | 0.938 | 0.687 | 0.595 | *0.733* |
| 0.50 | 0.867 | 0.643 | 0.615 | *0.817* |
| 0.75 | 0.742 | 0.550 | 0.541 | *0.567* |
| 1.00 (overlaps benign) | **0.561** | **0.392** | 0.470 | *0.650* |

### Alert queue quality — and what the false positives actually are

The ranking fix removed the alert-size confound: **corr(alert_score, alert size) = 0.042**
(was 0.263, when 19 of the top 30 alerts were service accounts against 30% of traffic).

Top-20 contains 7 true positives. The other 13 are **not random noise**:

Counts are absolute within each window and sum to it (malicious + false positives = N):

| window | malicious | FPs | composition of the false positives |
|---|---|---|---|
| top 20 | 7 | 13 | 10 `password_reset_storm` · 3 `cert_retry_loop` |
| top 50 | 21 | 29 | 19 `password_reset_storm` · 3 `cert_retry_loop` · 2 `maintenance_window` · 2 `business_travel` · **3 ordinary benign** |
| top 100 | 40 | 60 | 19 `password_reset_storm` · 9 `business_travel` · 5 `maintenance_window` · 3 `cert_retry_loop` · 3 `os_patch` · 1 `shared_jump_host` · 1 `oncall_rotation` · **19 ordinary benign** |

**Only 3 ordinary-benign false positives in the top 50, and none at all in the top 20.** A password-reset storm is many
failed authentications from one entity in a short window — genuinely the same shape as
brute force. The detector's mistakes are the hard cases the confounders were injected at
4× the attack rate to create.

> **Correction to an earlier draft of this report**, which claimed 17/20 malicious in the
> top 20. That figure was measured on a generator that was later found to be leaking
> (see §1, defects 5–7) — part of that apparent queue quality came from the leak. 7/20
> against engineered confounders is the honest number, and the FP-composition table above
> is the meaningful result.

### Anomaly type attribution

Rule-based over the evidence vector, on detected alerts:

| actual class | correct | of | rate |
|---|---|---|---|
| credential_stuffing | 93 | 98 | 0.949 |
| lateral_movement | 13 | 14 | 0.929 |
| impossible_travel | 6 | 7 | 0.857 |
| device_spoofing | 11 | 15 | 0.733 |
| brute_force | 1 | 2 | 0.500 |
| **low_and_slow** | **17** | **67** | **0.254** — 49 go to `lateral_movement` |
| `insider_drift` | 0 | 29 | **0.000** — see below |
| **total** | **141** | **232** | **0.608** |

`insider_drift` scores 0/29 **by construction, not by failure**: it is the ambiguous edge
case, deliberately excluded from `ATTACK_TYPES`, and there is no `insider_drift` rule for
the attributor to select — so it can never be predicted correctly. Its 29 alerts are
attributed to whichever attack type they most resemble (21 to `lateral_movement`), which is
the honest behaviour for a class the system is not asked to name.

Over the six real attack types alone, excluding that unpredictable class, accuracy is
**141/203 = 0.695**. Both figures are given because quoting only 0.695 would hide 29 alerts
the analyst does see, and quoting only 0.608 penalises the classifier for a class with no
target label.

Attribution scores the **max over all member events per signal**, not one representative
event. Scoring a single "best" event chosen by entity-level z made credential stuffing's
defining evidence — IP fan-out across many entities, which peaks on *different* events —
structurally invisible: accuracy was 0.470 and 13 stuffing campaigns were misread as brute
force. Fixing it took stuffing from 60/98 to 93/98 and that leak to zero.

The dominant remaining error is the documented `low_and_slow` / `lateral_movement` overlap,
measured separately at ROC-AUC 0.810 [0.780, 0.835]. `low_and_slow` attribution is
**17/67**, up only marginally from 9/40 — nearly all of the 0.470 → 0.608 gain came from
the credential-stuffing fix, not from this pair.

A rebalance onto the strongest event-level discriminators for this pair was attempted and
made things **worse** (17/67 → 1/67, overall 0.608 → 0.547) for a structural reason:
burst-shaped and absence-shaped attacks need opposite evidence aggregations. See
limitation 16.

### Held-out seeds — the protocol

Config frozen to `frozen_config.json` (**sha256[:16] `10284ea8d70452c5`**) *before* the

| seed | prevalence | Incident recall | Precision@1% | R-Precision | PR-AUC |
|---|---|---|---|---|---|
| 101 | 1.9% | 0.729 | 0.849 | 0.556 | 0.610 |
| 102 | 1.8% | 0.764 | 0.864 | 0.507 | 0.572 |
| 103 | 0.7% | 0.800 | 0.474 | 0.590 | 0.612 |
| 104 | 0.9% | 0.972 | 0.597 | 0.628 | 0.647 |

Note the inverse relationship between prevalence and Precision@1%: the three lowest-

**All datasets were regenerated** after every generator change — four full regenerations

### Cold start — measured, not merely implemented

New entities are shrunk toward the cohort prior with weight `n/(n+50)`, and novelty flags
are scaled by that same weight, so "never seen before" fires weakly for an entity with no
history. The measured outcome:

| | |
|---|---|
| cold-start events | 4,375 (3.3% of stream) |
| attack rate, cold vs warm | 4.73% vs 1.90% — **2.49×** |
| share of the top-1% alert budget | 13.0% |
| **precision of cold-start alerts** | **95.9%** |
| precision of warm alerts | 85.4% |
| Precision@1% excluding cold-start | 0.861 (vs 0.867 including) |

Cold-start entities take 13.0% of the budget while being 3.3% of traffic — a 3.9×
over-representation that is **earned rather than a shrinkage failure**. Those alerts are
the highest-precision alerts in the queue, cold-start events genuinely carry 2.49× the
attack rate, and removing them *lowers* Precision@1%.

Judging this by share alone would have been the wrong test and would have reported a
failure: an equal share would have meant the detector was under-weighting a genuinely
attack-denser subset.

### Streaming performance

Same code path as the batch evaluation — no batch/stream skew. Measured on seed 3, 20,000
events after a 2,000-event warm-up:

| | |
|---|---|
| throughput | **3,281 events/sec** (single Python process) |
| p50 latency | 0.268 ms |
| p95 / p99 | 0.502 / 0.753 ms |
| max | 3.40 ms |
| state per entity | 1.3 kB |

Two optimisations account for most of this: a precomputed z lookup table (replacing 20
scipy `norm.ppf` scalar calls per event) and a dict-based single-event scoring path
(replacing a one-row DataFrame construction). Earlier drafts of this report quoted 1,200
ev/s and 1,815 ev/s — both were measured mid-refactor and are superseded by the figures
above.

p50 varies roughly 0.3–5 ms between runs on this loaded developer machine, so treat these
as indicative rather than tight. One 98-second single-event outlier was observed once and
did not reproduce across a 12,000-event re-run (max 18.6 ms) — an OS stall, not a code path.

Production mapping (`src/stream.py`): Kafka partitioned **by entity_id** so per-entity
state is worker-local and workers never coordinate → Flink/Kafka Streams → RocksDB state
store → scorer → ranked alert queue. The IP-level detector is the exception, since
credential stuffing is cross-entity by definition, and needs a second stream keyed by
`source_ip` — a standard co-partitioning trade-off, and part of why the levels are kept
separate rather than fused.

## 6. Cold start and concept drift

**Cold start** is described and measured in §5 ("Cold start — measured, not merely
implemented"). In brief: peer-group prior by `entity_type`, empirical-Bayes shrinkage
`λ = n/(n+50)`, novelty flags scaled by that same λ, and a `LOW CONFIDENCE — COLD START`
badge carrying the entity's actual history length. The measured outcome is that cold-start
alerts are the **highest-precision** alerts in the queue (95.9% vs 85.4% for warm), so
their 3.9× over-representation in the alert budget is earned rather than a shrinkage
failure.

**Drift and poisoning.** 30 matched attacker/legit pairs × 4 update arms
(`src/drift.py`). Days 30–44 are an exactly matched ramp — same schedule, same count of new
resources — because if the attacker ramped faster it would be detectable on rate alone and
the experiment would prove nothing. Only the *character* differs.

**What we demonstrated.** The adaptation/rigidity trade-off is real and large: a frozen
baseline raises **23.7** false alerts on a single legitimately-drifting entity over 30 days
versus **0.5** for adaptive updating — a ~47× cost for refusing to adapt.

**What we did not demonstrate** — see §7 (limitations 1 and 10).

## 7. Known limitations

Stated plainly, because each is a real weakness of what we built.

**1. Entity-level quarantine did not measurably resist poisoning.** Attacker score ratio
0.765 under quarantine vs 0.751 under naive updating — right direction, marginal at p=0.05,
overlapping intervals. The pre-registered claim (0.85 vs ≤0.15 absorption) is **not met**.
The likely cause is structural: the growth cap triggers on the entity's *own* historical
rate, so an attacker who ramps slowly enough simply drags that baseline along. Fixing it
needs a longer reference window than the 7 days used here — a design change, not a
parameter change. Reported as a negative result rather than tuned until it looked right.

**2. `low_and_slow` is under-escalated: 43% HIGH against a ≥70% target.** The band
objectives now fail on the opposite side from before. `insider_drift` **meets both of its
targets** — 4% HIGH (≤15% required) and 9% LOW (≤25% required), with 87% correctly landing
in MEDIUM — but the same suppression that achieved that has pushed `low_and_slow` down to
43% HIGH. Earlier drafts of this report recorded the reverse failure (`insider_drift` at
37% HIGH); that is fixed, and this is the cost. The two classes are near-identical by
construction, so the band objective can be met for one or the other, not yet both.

**3. Separating `insider_drift` from `low_and_slow` costs escalation and attribution, not detection.** The two
are near-identical by construction, so suppressing one necessarily suppresses the other.
Current position: `low_and_slow` campaign recall is 0.900 on the dev seed and 0.971 on the
holdout, but its HIGH-band share is 43% (limitation 2), and its type attribution is 17/67
(limitation 16). Detection survives the trade-off; escalation and attribution do not.

**4. `device_spoofing` is the weakest type after `impossible_travel`** — 0.800 campaign
recall on the dev seed but **0.657** averaged over five held-out seeds. At δ = 0.5 a spoof
changes two fingerprint fields, and the `os_patch` / `device_refresh` confounders change
two fields benignly, so this is substantially intended difficulty. The ablation shows it
depends almost entirely on L0: removing the deterministic rules drops it 0.80 → 0.30.

**5. The δ knob does not bite evenly across attack types.** Campaign recall range across
the whole sweep: `credential_stuffing` 0.10 (0.90 → 1.00, effectively pinned),
`device_spoofing` 0.20, `lateral_movement` 0.30, versus `brute_force` 0.50,
`impossible_travel` 0.50 and `low_and_slow` 0.50. Credential stuffing is essentially
unaffected by difficulty — many entities against few IPs stays visible at the IP level
however slow it goes — so its 1.000 should be read as "this benchmark never made it hard",
not as a detector result. The interpolation ranges for that type are too narrow.

**6. Alert-level calibration still uses ABSOLUTE size, not entity-relative rate.**
Calibrating away absolute size also removes genuine evidence for attacks whose signature
*is* volume. `burst_ratio` recovers part of it at the signal level by measuring activity
against the entity's own habitual rate (60.75 for brute force vs 1.05 for normal traffic),
but the alert scorer has not been reformulated the same way. Brute force now reaches 0.833
on the holdout, so the residual cost is modest — but the correct full fix is
entity-relative throughout, and it is not implemented.

**7. Incident recall is not monotone in difficulty.** It runs 0.600 / 0.733 / 0.817 /
0.567 / 0.650 across δ. This is a confound in the metric: prevalence falls 2.4% → 1.5%
across the sweep, so at low δ more campaigns compete for the same fixed budget and recall
saturates against the budget rather than against detector capability. `Precision@1%` and
`PR-AUC` are both monotone and are used as the headline degradation signals instead.

**8. The GRU was not built, and the ablation reprices what it would have been worth.**
The n-gram is in and wired into fusion; the GRU is **not implemented**, so the "GRU vs
n-gram" comparison is absent. The layer ablation (§3) supplies a more useful measurement:
across four eval seeds, L2's Precision@1% contribution is +0.008 with range
[−0.016, +0.024] — not distinguishable from zero. A GRU would have to beat a layer whose
marginal value cannot currently be detected. **Scoped caveat:** this benchmark's command
sequences come from a small per-entity Markov chain, on which n-gram surprisal is largely
recoverable from the per-event novelty L1 already provides. The null result is about this
generator's sequence structure, not about sequence modelling in general.

**9. The δ-sweep is one seed pair per point, with no error bars.** Each δ is a single
fit/eval pair, and prevalence varies across them (2.4% → 1.5%), which is the confound
behind limitation 7. Per-type recalls at any single δ move by ±0.2 between adjacent points
— e.g. `impossible_travel` reads 0.10, 0.20, 0.60, 0.20, 0.30 — which is sampling noise on
~10 campaigns per type, not a difficulty response. Several seeds per δ would be needed to
put intervals on the curve.

**10. `insider_drift` and `low_and_slow` do not converge as δ rises**, despite the
δ-dependent target blending added for exactly that purpose. Their HIGH-band shares show no
trend across the sweep. The blending lowered measured separability from 0.966 to 0.810 but
did not achieve the intended convergence at δ=1.

**11. Single-process throughput.** 3,281 events/sec is measured on one Python process on a
loaded developer machine, and p50 varies roughly 0.3-5 ms between runs; horizontal scaling
is argued from the partitioning design, not demonstrated on a cluster.

**12. Scale.** Results are at 175-200 entities over 56-65 days (132k-172k events per
dataset; CM8 randomises the requested 200 x 60 per seed). The generator is parameterised
for ~1M events but every reported number is at this smaller scale.

**13. Two of three installed dependencies are unused.** `lightgbm` is used (audit and L5
classifier). **`faker` and `shap` are installed but never imported**: the generator uses a
seeded internal ID/IP/MAC generator instead of faker, and the planned SHAP cross-check on
L5 was never implemented, so explainability rests entirely on the native evidence vector.
`torch` is likewise unused, following from limitation 8 (the GRU was never built). The install step can be dropped to
`pip install lightgbm` with no loss.

**14. User accounts still show 23 distinct source IPs (max 51).** The service-account and
edge-device cohorts were tightened to medians of 9 and 6, but human users were deliberately
left roaming — only humans should. 23 is still high for one person over 56 days and is a
third cohort-realism issue, reported alongside the other two rather than quietly fixed:
all three came from the same root cause, a `new_ip_rate` chosen for one population and
applied to all.

**15. Incident precision is bounded by the budget, near 0.12.** At the default operating
point an analyst reviews ~504 alerts over the window (9/day × 56 days) containing **60**
real campaigns, so incident precision is bounded at **0.119** before the detector does
anything — and it reaches **0.097**, i.e. 82% of what is achievable. The dashboard shows precision against that ceiling and
plots it as a function of budget, where it rises sharply as K falls — demonstrating the
bound is structural. The event-level `Precision@1%` is the number that is not
budget-bounded.

**16. Two attack classes require OPPOSITE evidence aggregations, and the pipeline can
only do one.** Alert-level attribution aggregates each signal as the **max over the
alert's member events**. That choice is what rescued credential stuffing — its defining
IP fan-out peaks on *some* member event, and scoring a single representative event made it
structurally invisible (60/98 → 93/98 correct once fixed). The same choice actively
destroys `low_and_slow`: that class is defined by what it *never* does — never bursts —
and a max erases exactly that property.

Measured directly: rebalancing the `low_and_slow` rule onto the strongest event-level
discriminators (`burst_ratio` 0.81 vs 1.65 for lateral movement, `cmd_surprisal` 3.93 vs
5.23) made attribution **worse**, 17/67 → **1/67**, and overall accuracy 0.608 → 0.547.
Reverted. `low_and_slow` sits at 17/67, up only marginally from 9/40 — nearly all of the
0.470 → 0.608 gain came from the credential-stuffing fix, not from this pair.

This is a structural property of the architecture rather than a tuning miss: burst-shaped
attacks need max aggregation, absence-shaped attacks need mean or a low quantile, and the
current pipeline applies one rule to both. Per-signal aggregation policy is the fix and it
is not implemented.

**17. Synthetic throughout.** Every behavioural assumption in §2 is ours. The confounders
and the δ-sweep are there to make the benchmark honest, but no synthetic dataset can
establish that these signals transfer to a real estate.

## 8. Reproducing

```bash
pip install lightgbm          # the only installed dependency actually used (see limitation 13)

# Datasets. Seed 3 is the eval/demo seed: it carries all six attack types.
python src/generator.py --seed 1 --entities 200 --days 60 --delta 0.5
python src/generator.py --seed 3 --entities 200 --days 60 --delta 0.5

# The gate comes first. Nothing downstream is meaningful until it passes on BOTH seeds.
python src/audit.py --tag seed1_delta05
python src/audit.py --tag seed3_delta05

python tests/test_evaluate.py                  # 13 hand-computed metric tests
python src/pipeline.py --explain 3             # headline metrics + sample alert panels
python src/classify.py                         # anomaly-type confusion matrix
python src/ablation.py                         # layer ablation: does each layer earn its keep
python src/drift.py                            # drift + poisoning, 30 matched pairs
python src/stream.py                           # latency benchmark
python src/experiments.py                      # δ sweep + frozen-config holdout run

streamlit run dashboard/app.py
```

`pipeline.py`, `classify.py` and `stream.py` default to `--fit seed1_delta05 --eval
seed3_delta05`.

`src/experiments.py` writes `frozen_config.json` with a content hash **before** the holdout
seeds are generated, and re-verifies the hash at scoring time, so "we did not tune on the
holdout" is checkable rather than asserted.

**If the generator is changed, every dataset must be regenerated and the gate re-run.**
Three separate leaks in this project were introduced by fixes that were themselves correct
(§1); the gate caught all three, but only because stale datasets were deleted rather than
reused.
